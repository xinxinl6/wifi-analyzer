## Native ICMP Ping 集成（解决华为应用市场上架审核问题）

### 背景
华为审核驳回原因：**非真实ICMP** — 原实现使用 TCP Socket 连接模拟 Ping（伪Ping），不符合网络工具规范。

### 解决方案
完全替换为系统级 **`OH_NetConn_QueryProbeResult`** C API，通过 C++ Native 模块 (NAPI) 调用。

### 新建文件
| 文件 | 用途 |
|------|------|
| `entry/src/main/cpp/CMakeLists.txt` | CMake 构建配置，链接 `libnet_connection.so` |
| `entry/src/main/cpp/ping_tool.h` | `PingNativeTool::Probe()` 接口定义 + `PingProbeResult` 结构体 |
| `entry/src/main/cpp/ping_tool.cpp` | 核心实现：调用 `OH_NetConn_QueryProbeResult(address, duration, &probeInfo)` |
| `entry/src/main/cpp/napi_init.cpp` | NAPI 绑定层：暴露 `nativeProbe(addr, dur)` → 返回 JSON Promise |
| `entry/src/main/ets/utils/NativePing.ets` | ArkTS 封装层：`NativePing.probe(address, mode)` |

### 修改文件
| 文件 | 改动内容 |
|------|---------|
| `entry/build-profile.json5` | 新增 `externalNativeOptions` 启用 C++ 编译 |

### 设计决策
- **无 TCP fallback**：用户明确要求移除所有 TCP Socket 伪 Ping 代码
- **双模式切换**：
  - 快速模式：`duration=1s`，每秒刷新一次
  - 准确模式：`duration=3s`，数据更精确（含标准差）
- **精度单位**：Native API 返回微秒(μs)，ArkTS 层转换为毫秒(ms) 显示
- **依赖**：需要 API 20+ / HarmonyOS 6.0+

## 统计卡片数字不更新修复（@Prop 复杂对象同步不可靠）

### 根因
`onStatsTickChanged()` 回调中读取 `this.sessionStats.sentCount`（`@Prop` 复杂对象 PingStats 接口），但 ArkTS `@Prop` 对接口/对象类型做引用比较/浅同步，父组件赋新对象后子组件仍可能读到旧值 → 本地 @State 副本永远为初始值 → UI 数字不更新。

### 修复方案：独立简单类型 @Prop 桥接
**核心思路**：不再依赖复杂对象 `@Prop sessionStats` 传递统计数据，改为拆成 8 个独立 `number` 类型的 `@Prop`，每个简单类型值 ArkTS 能可靠同步。

### 改动文件
| 文件 | 改动 |
|------|------|
| **PingTestingView.ets** | 新增 8 个 `@prop prop*`（propSentCount, propReceivedCount, propLossRate, propMaxTime, propMinTime, propAvgTime, propJitter, propStabilityScore）；`onStatsTickChanged()` 从这些独立 prop 读取而非 `this.sessionStats.*`；TestingViewProps 接口同步更新 |
| **PingTestPage.ets** | TestingView 调用处新增 8 个 prop 传参：`propSentCount: this.sessionStats.sentCount` 等 |

### 数据流
```
父组件 recalcStats() → this.sessionStats = {新对象}
  ↓
父组件 statsUpdateTick++ 
  ↓ (@Prop 简单类型 number，可靠同步)
子组件 @Watch('onStatsTickChanged') 触发
  ↓
读取 this.propSentCount 等（number @Prop，可靠）
  ↓
赋值给 this.localSentCount 等（@State，触发 UI 重绘 + 弹跳动画）
```

## DNS 查询引擎重构 — HTTP DNS (DoH) 真实多服务器

### 背景
原实现使用 `connection.getAddressesByName()` 系统API，**DNS 服务器选择器是假的**（选了不同服务器结果完全一样，始终走系统默认DNS），且只支持 A/AAAA 记录。

### 重构方案
改为 **HTTP DNS (DoH) JSON-over-HTTPS** 方式：
- 选了指定 DNS 服务器 → 通过 HTTPS 请求该服务器的 DoH JSON 接口（阿里/Google/Cloudflare）
- 选「系统默认」→ 仍走 connection API（兜底）
- 并行查询 A/AAAA/CNAME/MX/NS/TXT 全部 6 种记录类型

### 改动文件
| 文件 | 改动 |
|------|------|
| **DnsLookupEngine.ets** | 完全重写：新增 DoH 接口配置、`queryViaHttpDns()`/`parseDoHJson()` 方法、lookup() 分流逻辑 |
| **DnsLookupPage.ets** | `ServerItem` 新增 `apiUrl` 字段，`loadServers()` 同步映射 |

### DNS 服务器 DoH 配置
| 服务器 | API URL | 格式 |
|--------|---------|------|
| 阿里 | `https://dns.alidns.com/resolve?name={domain}&type={type}` | JSON |
| Google | `https://dns.google/resolve?name={domain}&type={type}` | JSON |
| Cloudflare | `https://cloudflare-dns.com/dns-query?...` | JSON (Accept: dns-json) |
| 腾讯/百度 | 已配置但暂为 wireformat 备用 |

### ArkTS 兼容性处理
- `Record<string, Object>` → `Record<string, Object \| string \| number \| boolean \| null>`
- `as DoHAnswerItem[]` 类型断言 + 显式 `typeof` 检查
- catch 必须绑定变量
- 所有接口显式声明（无内联对象字面量类型）

### 错误原因
`queryMyIp()` 方法中使用了内联对象字面量类型 `Array<{ url: string, parser: (text: string) => string }>`，ArkTS 禁止此写法（arkts-no-obj-literals-as-types / arkts-no-untyped-obj-literals）。同时 `JSON.parse` 返回值隐含 `any` 类型。

### 修复
1. 新增 `IpQueryApiEntry` 接口显式声明 `{ url, parser }` 结构
2. `Array<{...}>` → `IpQueryApiEntry[]`
3. `JSON.parse(t)` → `JSON.parse(t) as Record<string, string>` 消除 any
4. `catch { }` → `catch (e) { }` （ArkTS 要求 catch 必须绑定变量）

## 首页 WiFi 连接卡片"未连接" Bug 修复

### 问题

- `@Consume('wifiState')` 添加 `@Watch('onWifiStateChange')`
- 新增回调方法：wifiState 变化时自动调 `updateState()` 重算 connected/signalColor

## 权限弹窗流程修复（华为审核驳回 #2）

### 问题
华为审核测试步骤：首次进入应用 → 提示获取位置权限 → 跳转设置页面 **无获取位置权限选项** → 需删除后台后进入应用才弹出权限申请

### 根因分析
1. **无返回重检机制**：`requestPermissionsAndScan()` 只在 `aboutToAppear()` 执行一次，从设置页返回后没有任何生命周期钩子触发重检
2. **设置页跳转目标不准**：`openAppSettings()` 首先尝试 `application_info_entry`，某些华为设备上该页面不直接展示权限管理入口

### 修复方案

#### 1. Index.ets — 新增 `onPageShow()` 生命周期钩子
- 页面每次变为可见时触发（包括从设置页返回、从后台恢复）
- 条件：`privacyAgreed && !permissionGranted` → 调用 `recheckPermissionsOnReturn()`
- 避免隐私弹窗期间重复触发（隐私未同意时不执行）

#### 2. Index.ets — 新增 `recheckPermissionsOnReturn()` 异步方法
- 重新获取 context（abilityContext 可能为空时 fallback 到 `getUIContext().getHostContext()`）
- 调用 `PermissionManager.requestPermissions(context)` 重新检查+请求
- 已授权 → 关闭弹窗 + 开始扫描
- 仍未授权 → 重新显示权限引导弹窗

#### 3. PermissionManager.ets — `openAppSettings()` URI 顺序优化
- **方法1(新增)**: `uri: 'permission_manager_apps'` — 直接打开应用权限管理页（优先）
- 方法2: `application_info_entry` — 应用详情页
- 方法3-4: OpenHarmony 对应 URI
- 方法5-6: 设置主页兜底 / 隐式 Want

#### 4. Index.ets — 权限拒绝弹窗文案优化
- 提示文字简化：「请点击「去设置」开启位置信息权限，**返回应用后我们将自动继续**」
- 按钮文案：「打开设置」→「去设置」

### 改动文件汇总
| 文件 | 改动 |
|------|------|
| **Index.ets** | 新增 `onPageShow()` + `recheckPermissionsOnReturn()`；优化弹窗文案和按钮文字 |
| **PermissionManager.ets** | `openAppSettings()` 新增 `permission_manager_apps` 作为首选 URI |

## "去设置"白屏 Bug 修复

### 问题
点击权限拒绝弹窗的「去设置」按钮 → 跳转到一个**白屏页面**（只有左上角返回箭头），无法进行任何权限操作。

### 根因
`openAppSettings()` 首选方案使用了 `uri: 'permission_manager_apps'`：
- **`startAbility()` 对无效/不兼容的 URI 不会抛异常**！它"成功"打开了设置应用的一个空 Ability 页面，直接返回了 `true`
- fallback 链（application_info_entry、settings main 等）**从未执行**，因为代码认为已经成功了
- 实际上该 URI 在用户设备的 HarmonyOS 版本上渲染为空白页

### 修复 (PermissionManager.ets — `openAppSettings()` 完全重写)

**核心策略变更：按稳定性排序 + 增强日志**

| 优先级 | URI | 理由 |
|--------|-----|------|
| ① **`application_info_entry`** | 最稳定，各版本华为设备表现一致；用户可在详情页找到"权限"入口 |
| ② 设置主页（无URI） | **100% 能打开**（无 URI 参数不会白屏）；用户手动导航到 应用→权限 |
| ③ `permission_manager_apps` | ⚠️ 某些系统版本可能白屏！仅作最后尝试 |
| ④ OpenHarmony 兼容 | 模拟器 / 纯 OHOS 设备 |
| ⑤ 隐式 Want | 最终兜底 |

**日志增强**：每个方法用 ✅ accepted / ❌ rejected 标记，方便 hilog 排查实际走了哪个分支

**关键注释**：记录踩坑经验——`startAbility` 对无效 URI 不抛异常而是打开白屏页
