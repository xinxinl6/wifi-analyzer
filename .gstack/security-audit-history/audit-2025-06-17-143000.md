# WiFi Analyzer HarmonyOS 应用 — 安全审计报告

## Meta
- **审计模式**: Comprehensive（全面审计）
- **日期**: 2025-06-17
- **范围**: 全部5个模块（entry, core, tools, speed-test, design-system）+ NAPI C++ 层 + 基础设施配置
- **执行阶段**: 14/14

---

## Executive Summary

本次审计对 WiFi Analyzer HarmonyOS 应用进行了全面安全评估。发现 **1个严重漏洞、4个高危漏洞、5个中危漏洞、4个低危/建议项**。最严重的问题是 **构建配置中明文存储签名密钥密码**（build-profile.json5），以及 **发布签名证书(.p12/.p7b/.cer)存储在项目仓库中且未被 .gitignore 排除**。此外，多处使用 HTTP 明文通信、日志泄露 WiFi BSSID/SSID 信息、WebView 未做安全限制等问题需要上线前修复。

**整体安全结论：条件 Go** — 修复严重和高危项后可上线。

## Findings

### 🔴 F-001: 签名密钥密码明文存储在构建配置中
- **Category**: OWASP A02 / STRIDE: Information Disclosure
- **Severity**: 🔴 严重 (Critical)
- **Confidence**: 10/10
- **Location**: `build-profile.json5:10-14`
- **Description**: 构建配置文件中包含明文的 keyPassword 和 storePassword。这些是 HarmonyOS 应用签名密钥的保护密码，以明文 Hex 编码存储。任何能访问代码仓库的人都可以提取签名证书并伪造应用更新。
- **Exploit Scenario**: 1) 攻击者获取仓库访问权 → 2) 从 build-profile.json5 提取 keyPassword/storePassword → 3) 使用 .p12 证书文件签名恶意应用 → 4) 冒充官方应用分发恶意版本
- **Reproduction Steps**: 1) 打开 `build-profile.json5` → 2) 定位到 `signingConfigs[0].material` → 3) 可见 `keyPassword: "0000001BA3DEE..."` 和 `storePassword: "0000001BE7CF..."`
- **Remediation**: 
  1. 将签名配置从 build-profile.json5 移除，改为使用环境变量或 CI 密钥管理
  2. 在 .gitignore 中添加 `build-profile.json5` 或仅保留不含密钥的模板
  3. 立即轮换已暴露的签名密钥
  4. 使用 `ohsign` 命令行工具在 CI 中签名，不将密码写入文件
- **Priority**: P0（立即修复）

### 🔴 F-002: 发布签名证书存储在项目目录中且未被 gitignore 排除
- **Category**: OWASP A02 / STRIDE: Information Disclosure
- **Severity**: 🔴 严重 (Critical)
- **Confidence**: 10/10
- **Location**: `Key/` 目录（`wifi-analyzer-release.p12`, `wifi-analyzer-release.cer`, `wifi-analyzer-profileRelease.p7b`, `wifi-analyzer-release.csr`）
- **Description**: 项目根目录下的 `Key/` 文件夹包含了完整的发布签名证书链（.p12 私钥文件、.cer 证书、.p7b 配置文件、.csr 请求文件）。项目根目录没有 .gitignore 文件，这些证书可能已被提交到版本控制。
- **Exploit Scenario**: 1) 证书文件被推送到远程仓库 → 2) 任何有仓库读权限的人获取 .p12 文件 → 3) 配合 F-001 的密码签名恶意应用
- **Reproduction Steps**: 1) `ls Key/` → 2) 可见 `wifi-analyzer-release.p12`（私钥）、`.cer`（证书）、`.p7b`（profile）
- **Remediation**:
  1. 在项目根目录创建 `.gitignore`，添加 `Key/`、`build-profile.json5`、`*.p12`、`*.p7b`、`*.cer`、`*.csr`
  2. 使用 `git filter-branch` 或 BFG Repo-Cleaner 从历史中清除已提交的证书文件
  3. 轮换已暴露的发布证书（联系华为开发者重新申请）
  4. 将证书存储在安全的密钥管理服务中，仅在 CI 构建时注入
- **Priority**: P0（立即修复）

### 🟠 F-003: IP 地理查询使用 HTTP 明文通信
- **Category**: OWASP A02 / STRIDE: Information Disclosure + Tampering
- **Severity**: 🟠 重要 (High)
- **Confidence**: 9/10
- **Location**: `tools/src/main/ets/ipgeo/IpGeoEngine.ets:62,67,179`
- **Description**: IP 地理位置查询使用 `http://ip-api.com/json/` 和 `http://whois.pconline.com.cn/ipJson.jsp` 等 HTTP 明文 API。用户的公网 IP 和查询目标 IP 在传输过程中完全暴露，可被中间人攻击者截获或篡改响应数据。
- **Exploit Scenario**: 1) 用户在公共 WiFi 下查询 IP 归属地 → 2) 中间人截获 HTTP 请求 → 3) 获取用户公网 IP 和地理位置信息 → 4) 或篡改响应返回虚假地理位置
- **Reproduction Steps**: 1) 查看 `IpGeoEngine.ets` 第 62 行和 179 行 → 2) 确认使用 `http://` 而非 `https://`
- **Remediation**:
  1. 将 `http://ip-api.com/json/` 改为 `https://ip-api.com/json/`（该 API 支持 HTTPS）
  2. 将 `http://whois.pconline.com.cn/ipJson.jsp` 替换为支持 HTTPS 的替代 API
  3. 对所有外部 API 调用强制使用 HTTPS
- **Priority**: P1（本迭代修复）

### 🟠 F-004: Traceroute/LAN扫描/端口扫描使用 HTTP 明文探测
- **Category**: OWASP A02 / A10 (SSRF)
- **Severity**: 🟠 重要 (High)
- **Confidence**: 9/10
- **Location**: 
  - `tools/src/main/ets/traceroute/TracerouteEngine.ets:252`
  - `tools/src/main/ets/lanscan/LanEngine.ets:149`
  - `tools/src/main/ets/ports/PortScanEngine.ets:119`
- **Description**: Traceroute 使用 `http://${target}` 明文请求探测，局域网扫描使用 `http://${ip}:${port}` 端口探测，端口扫描使用 `http://${address}:${port}` 探测。这些明文 HTTP 请求：(1) 暴露用户正在探测的目标信息；(2) 在 Traceroute 中，用户输入直接拼接到 URL 中，存在 SSRF 风险；(3) 响应可能被篡改。
- **Exploit Scenario**: 1) 中间人截获 Traceroute 的 `http://target` 请求 → 2) 知道用户正在 trace 的目标 → 3) 或篡改响应延迟数据，误导用户判断网络状况
- **Reproduction Steps**: 1) 查看 `TracerouteEngine.ets` 第 252 行 `http://${target}` → 2) 查看 `LanEngine.ets` 第 149 行 `http://${ip}:${port}` → 3) 查看 `PortScanEngine.ets` 第 119 行
- **Remediation**:
  1. Traceroute: 改用 TCP socket 连接（而非 HTTP 请求）测量延迟
  2. LAN 扫描: 使用 TCP socket connect 探测端口，而非 HTTP 请求
  3. 端口扫描: 同上，使用 TCP socket connect 替代 HTTP HEAD
  4. 如必须使用 HTTP，至少改用 HTTPS
- **Priority**: P1（本迭代修复）

### 🟠 F-005: 日志中泄露 WiFi SSID 和 BSSID 信息
- **Category**: OWASP A09 / STRIDE: Information Disclosure
- **Severity**: 🟠 重要 (High)
- **Confidence**: 9/10
- **Location**: 
  - `core/src/main/ets/wifi/WifiScanner.ets:171-172`（BSSID+SSID 明文输出）
  - `core/src/main/ets/wifi/WifiDataManager.ets:78,103,112,122,129`（SSID+BSSID 明文输出）
  - `tools/src/main/ets/traceroute/TracerouteEngine.ets:75,98`（gateway/DNS 明文输出）
- **Description**: hilog 和 console.info 中直接输出 WiFi SSID、BSSID、网关 IP、DNS 服务器地址等敏感网络信息。虽然使用了 `%{public}s` 格式化，但在 HarmonyOS 调试模式下这些日志是可读的。SSID + BSSID 组合可唯一标识用户所在的物理位置，构成位置隐私泄露。
- **Exploit Scenario**: 1) 恶意应用通过读取系统日志 → 2) 获取用户当前连接的 WiFi SSID + BSSID → 3) 通过 WiFi 定位数据库反推用户物理位置
- **Reproduction Steps**: 1) 在 WifiScanner.ets 第 171 行可见 `hilog.info(... 'Connected to: ' + result.connectedSsid + ', RSSI: ' + ... ', BSSID: ' + result.connectedBssid)` → 2) BSSID 可直接用于 WiFi 定位
- **Remediation**:
  1. 在 Release 构建中移除所有包含 SSID/BSSID 的日志输出
  2. 如需调试日志，对 SSID 做脱敏处理（如只显示前3字符+***）
  3. BSSID 在日志中应完全隐藏或仅显示 OUI 部分（前3字节）
  4. `LoggerConfig.level` 在 Release 构建时应设置为 `LogLevel.NONE`（当前为 `LogLevel.DEBUG`）
- **Priority**: P1（本迭代修复）

### 🟠 F-006: WebView 加载外部 URL 无安全限制
- **Category**: OWASP A05 / STRIDE: Tampering + Elevation of Privilege
- **Severity**: 🟠 重要 (High)
- **Confidence**: 8/10
- **Location**: `entry/src/main/ets/components/AuroraAIModule.ets:272`
- **Description**: AI 分析功能使用 WebView 加载百度搜索 URL，但未配置以下安全措施：
  1. 无 URL 白名单验证（可导航到任意网站）
  2. 未禁用 JavaScript（默认启用，存在 XSS 风险）
  3. 未禁用文件访问（`fileAccess`、`fileFromUrlAccess`）
  4. 未设置安全 CSP
  5. 未禁用 `domStorage`
- **Exploit Scenario**: 1) 恶意搜索结果或百度页面被注入恶意 JS → 2) WebView 中的 JS 读取本地文件或执行钓鱼攻击 → 3) 如果 WebView 有桥接对象，可能调用本地功能
- **Reproduction Steps**: 1) 查看 `AuroraAIModule.ets` 第 272 行 `Web({ src: this.aiWebViewUrl, controller: ... })` → 2) 未看到 `.javaScriptAccess(false)` 或 `.fileAccess(false)` 配置
- **Remediation**:
  1. 添加 URL 白名单验证（仅允许 `m.baidu.com` 和 `www.baidu.com`）
  2. 配置 `javaScriptProxy` 仅暴露必要接口
  3. 禁用文件访问: `.fileAccess(false)` `.fileFromUrlAccess(false)`
  4. 添加 `onUrlLoadIntercept` 回调，拦截非白名单 URL 跳转
  5. 考虑使用 `onSslErrorReceive` 处理 SSL 错误
- **Priority**: P1（本迭代修复）

### 🟡 F-007: DataPreferences 明文存储 DNS 查询历史和 Ping 历史
- **Category**: OWASP A02 / STRIDE: Information Disclosure
- **Severity**: 🟡 一般 (Medium)
- **Confidence**: 8/10
- **Location**: 
  - `tools/src/main/ets/dnslookup/DnsLookupEngine.ets:126-197`
  - `entry/src/main/ets/utils/PingStorage.ets:27-152`
- **Description**: DNS 查询历史和 Ping 历史使用 `@ohos.data.preferences` 存储，该存储是明文 KV 存储。在已 root 的设备上，其他应用可以读取这些数据。DNS 查询历史可以揭示用户访问的域名，构成隐私泄露。
- **Exploit Scenario**: 1) 设备被 root → 2) 恶意应用读取 preferences 文件 → 3) 获取用户 DNS 查询历史 → 4) 推断用户访问的网站
- **Reproduction Steps**: 1) 查看 `DnsLookupEngine.ets` 第 191 行 `await pref.put(PREF_KEY, jsonStr)` → 2) 数据以明文 JSON 存储
- **Remediation**:
  1. 对敏感历史数据使用 `@ohos.data.relationalStore`（加密数据库）替代 preferences
  2. 或对 JSON 数据进行加密后再存储（使用 `@ohos.security.cryptoFramework`）
  3. 至少对域名做脱敏处理后再存储
  4. 提供"无痕模式"选项，不保存历史记录
- **Priority**: P2（下一迭代）

### 🟡 F-008: NAPI NativePing 缺少输入长度限制
- **Category**: OWASP A03 / STRIDE: Tampering
- **Severity**: 🟡 一般 (Medium)
- **Confidence**: 7/10
- **Location**: `entry/src/main/cpp/napi_init.cpp:140-144`
- **Description**: NativeProbe 函数从 ArkTS 接收地址字符串，虽然做了类型检查（napi_string），但未限制字符串长度。理论上可以传入超长字符串导致内存分配异常。此外，`duration` 参数仅做了类型检查，未验证范围（负数或超大值）。
- **Exploit Scenario**: 1) 恶意调用 `nativeProbe` 传入超长字符串 → 2) `new char[strLen + 1]` 可能分配大量内存 → 3) 或传入 `duration = -1` 或 `duration = 999999` 导致异常行为
- **Reproduction Steps**: 1) 在 napi_init.cpp 第 141 行，`napi_get_value_string_utf8` 获取字符串长度后直接分配 → 2) 未检查 `strLen > MAX_ADDRESS_LEN` → 3) 第 135 行 `napi_get_value_int32` 获取 duration 但未验证范围
- **Remediation**:
  1. 添加地址字符串最大长度限制（如 256 字节）
  2. 验证 duration 范围（1-30 秒）
  3. 在 C++ 层对地址格式做基本验证（IP 或域名字符集）
  4. 对 `OH_NetConn_QueryProbeResult` 的返回值做更严格的校验
- **Priority**: P2（下一迭代）

### 🟡 F-009: 端口扫描 SSRF 防护不完整
- **Category**: OWASP A10 (SSRF)
- **Severity**: 🟡 一般 (Medium)
- **Confidence**: 7/10
- **Location**: `tools/src/main/ets/ports/PortScanEngine.ets:243-265`
- **Description**: 端口扫描引擎的 `isValidTarget` 方法存在 SSRF 防护，但防护不完整：
  1. 仅检查 IPv4 内网地址，未检查 IPv6 内网地址（如 `::1`、`fd00::`）
  2. 仅检查了 `169.254.169.254`，未检查其他链路本地地址范围（169.254.0.0/16）
  3. 对域名目标没有限制（可解析到内网 IP 的域名）
  4. 未检查 `0.0.0.0`、`[::]` 等特殊地址
- **Exploit Scenario**: 1) 用户输入域名 `internal.corp.local` → 2) 域名通过验证（不是 IP） → 3) DNS 解析到 `192.168.1.1` → 4) 端口扫描访问到内网服务
- **Reproduction Steps**: 1) 查看 `isValidTarget` 方法 → 2) 注意仅检查 IPv4 内网，域名无限制
- **Remediation**:
  1. 对域名目标，先做 DNS 解析，再检查解析结果的 IP 是否为内网地址
  2. 添加 IPv6 内网地址检查（`::1`、`fc00::/7`、`fe80::/10`）
  3. 拒绝整个 169.254.0.0/16 链路本地范围
  4. 拒绝 `0.0.0.0` 和 `[::]` 地址
  5. 拒绝云元数据域名（如 `metadata.google.internal`）
- **Priority**: P2（下一迭代）

### 🟡 F-010: 上传测速完全模拟，无真实测量
- **Category**: OWASP A04 (Insecure Design)
- **Severity**: 🟡 一般 (Medium)
- **Confidence**: 8/10
- **Location**: `speed-test/src/main/ets/SpeedTestEngine.ets:329-347`
- **Description**: 上传测速完全基于下载速度的比例模拟（25%-50%），使用 `Math.random()` 生成结果，没有实际的上传测试。这构成虚假数据展示，可能误导用户对网络质量的判断。
- **Exploit Scenario**: 1) 用户依赖上传速度数据判断网络是否满足视频会议需求 → 2) 显示的"上传速度"是随机模拟值 → 3) 用户做出错误决策
- **Reproduction Steps**: 1) 查看 `measureUploadSimulated` 方法 → 2) 可见 `const ratio = 0.25 + Math.random() * 0.25` → 3) 无真实网络上传操作
- **Remediation**:
  1. 在 UI 中明确标注"上传速度为估算值"
  2. 或实现真实的上传测速（向测速服务器 POST 数据）
  3. 至少使用基于历史数据的估算而非纯随机值
- **Priority**: P2（下一迭代）

### 🟡 F-011: LoggerConfig 在 Release 中仍为 DEBUG 级别
- **Category**: OWASP A05 (Security Misconfiguration)
- **Severity**: 🟡 一般 (Medium)
- **Confidence**: 8/10
- **Location**: `core/src/main/ets/config/NetworkConfig.ets:246`
- **Description**: `LoggerConfig.level` 默认值为 `LogLevel.DEBUG`，注释说"发布时应设置为 WARN 或 NONE"，但代码中没有任何构建模式判断逻辑来自动切换日志级别。Release 构建将输出所有 DEBUG 日志，包括前述的 SSID/BSSID 等敏感信息。
- **Exploit Scenario**: 1) Release 构建的应用 → 2) 日志级别仍为 DEBUG → 3) 系统日志中包含大量敏感网络信息
- **Reproduction Steps**: 1) 查看 `LoggerConfig.level = LogLevel.DEBUG` → 2) 无构建模式检查
- **Remediation**:
  1. 使用构建变体自动设置日志级别：`static level: LogLevel = BuildConfig.DEBUG ? LogLevel.DEBUG : LogLevel.WARN`
  2. 或在 `EntryAbility.onCreate` 中根据构建模式设置 `LoggerConfig.level`
  3. Release 构建至少应为 WARN 级别
- **Priority**: P1（本迭代修复）

### 🟢 F-012: 权限声明合理但可进一步精简
- **Category**: OWASP A01 (Broken Access Control)
- **Severity**: 🟢 建议 (Info)
- **Confidence**: 9/10
- **Location**: `entry/src/main/module.json5:16-44`
- **Description**: 应用声明了 5 个权限：GET_WIFI_INFO、LOCATION、APPROXIMATELY_LOCATION、INTERNET、GET_NETWORK_INFO。权限使用场景声明了 `usedScene.when: "inuse"`，这是合理的。但 `LOCATION` 和 `APPROXIMATELY_LOCATION` 对于 WiFi 扫描功能是必需的（HarmonyOS 要求位置权限才能获取扫描结果），这一点是合规的。整体权限声明是合理的。
- **Remediation**: 无需修改，当前权限声明是 WiFi 分析仪应用的最小必要集合。
- **Priority**: P3（backlog）

### 🟢 F-013: NAPI C++ 层代码安全性较好
